# 02 — CDS Data Modeling

CDS (Core Data Services) is the backbone of every CAP application. Good modeling decisions at this layer have a compounding positive effect on maintainability, performance, and security.

---

## Namespaces

Every project must declare a namespace at the top of each schema file.

```cds
// GOOD
namespace com.company.sales;

entity Orders { ... }
entity Customers { ... }
```

```cds
// BAD — no namespace means global pollution and naming conflicts
entity Orders { ... }
```

Use the convention `com.{company}.{domain}`. For multi-domain projects, use one namespace per domain schema file.

---

## Entity Design

### Always Use Managed Keys

Prefer `UUID` as the primary key. Never use composite keys as the primary key — use unique constraints instead.

```cds
// GOOD
entity Products {
  key ID   : UUID;                     // auto-generated by CAP
  code     : String(10) not null;
  ...
}
```

```cds
// BAD — composite primary key
entity Products {
  key code    : String(10);
  key version : Integer;
}
```

### Use `cuid` and `managed` Aspects

CAP provides built-in aspects. Use them.

```cds
using { cuid, managed } from '@sap/cds/common';

entity Orders : cuid, managed {
  // Inherits: ID (UUID), createdAt, createdBy, modifiedAt, modifiedBy
  status   : String(20) default 'OPEN';
  customer : Association to Customers;
}
```

| Aspect | Fields added |
|--------|-------------|
| `cuid` | `ID : UUID` |
| `managed` | `createdAt`, `createdBy`, `modifiedAt`, `modifiedBy` |

### Element Nullability

Be explicit about nullability. Never rely on implicit defaults.

```cds
// GOOD — explicit constraints
entity LineItems {
  key ID        : UUID;
  quantity      : Integer not null;
  unitPrice     : Decimal(15,2) not null;
  description   : String(500);          // nullable — explicitly allowed
}
```

### Enumerations

Define enumerations as CDS types, not magic strings scattered across handlers.

```cds
// GOOD
type OrderStatus : String(20) enum {
  Open      = 'OPEN';
  Confirmed = 'CONFIRMED';
  Shipped   = 'SHIPPED';
  Cancelled = 'CANCELLED';
}

entity Orders : cuid, managed {
  status : OrderStatus default 'OPEN';
}
```

```cds
// BAD — magic string, no type safety
entity Orders {
  status : String(20);  // could be anything
}
```

## Associations and Compositions

### When to Use Each

| Relationship | Use When |
|-------------|----------|
| `Association` | Entities have independent lifecycles (e.g., `Order → Customer`) |
| `Composition` | Child cannot exist without parent (e.g., `Order → OrderItems`) |

```cds
entity Orders : cuid, managed {
  customer : Association to Customers;        // independent lifecycle
  items    : Composition of many OrderItems   // dependent lifecycle
              on items.order = $self;
}

entity OrderItems : cuid {
  order     : Association to Orders;
  product   : Association to Products;
  quantity  : Integer not null;
  unitPrice : Decimal(15,2) not null;
}
```

### Managed Associations vs Backlinks

Always define backlinks (the `on` condition) for to-many associations. For to-one associations, use the generated foreign key fields.

```cds
// GOOD — CAP manages the FK automatically
entity Orders {
  customer   : Association to Customers;
  // CAP generates: customer_ID : UUID
}

// GOOD — explicit backlink for to-many
entity Customers {
  orders : Association to many Orders on orders.customer = $self;
}
```

### Association Cardinality

Always annotate cardinality explicitly for clarity:

```cds
entity Orders {
  // to-one (default) — implicit
  customer : Association to Customers;

  // to-many — must be explicit
  items : Composition of many OrderItems on items.order = $self;
}
```

## Reusable Types and Aspects

Define reusable types in a dedicated file `db/types.cds` or directly use `@sap/cds/common`.

```cds
// db/types.cds
namespace com.company.common;

type Email    : String(320);
type Phone    : String(30);
type Currency : String(3);
type Amount   : Decimal(15,2);

aspect Auditable {
  createdAt  : Timestamp @cds.on.insert: $now;
  modifiedAt : Timestamp @cds.on.update: $now;
}
```

```cds
// db/schema.cds
using { com.company.common } from './types';

entity Customers : cuid {
  email : common.Email not null;
  phone : common.Phone;
}
```

## Views and Projections

Use CDS views to reshape data for specific contexts. Never create SQL views directly in HANA for logic that belongs in CDS.

```cds
// GOOD — CDS view/projection
view OrderSummary as select from Orders {
  ID,
  status,
  customer.name as customerName,
  count(items.ID) as itemCount : Integer,
  sum(items.quantity * items.unitPrice) as totalAmount : Decimal(15,2)
}
group by Orders.ID, Orders.status, customer.name;
```

## Services vs Schema

**The schema defines the domain model. Services define what gets exposed.**

Never expose internal entities directly from `db/` in a service without a projection. Always use projections to control what fields are visible.

```cds
// srv/catalog-service.cds

using { com.company.sales as db } from '../db/schema';

service CatalogService {

  // GOOD — project only what clients need
  entity Products as projection on db.Products
    excluding { internalCostPrice, supplierID };

  // BAD — never do this
  // entity Products as projection on db.Products; // exposes all fields including sensitive ones
}
```

## Annotations

### OData and Fiori Annotations

Keep OData/Fiori annotations in a separate file to avoid polluting the schema:

```
srv/
├── catalog-service.cds           # Service definition
├── catalog-service.js            # Handler
└── catalog-service-fiori.cds     # Fiori/UI annotations
```

```cds
// srv/catalog-service-fiori.cds
using CatalogService from './catalog-service';

annotate CatalogService.Products with @(
  UI.LineItem: [
    { Value: code,        Label: 'Product Code' },
    { Value: name,        Label: 'Name' },
    { Value: price,       Label: 'Price' }
  ],
  UI.HeaderInfo: {
    TypeName: 'Product',
    TypeNamePlural: 'Products',
    Title: { Value: name }
  }
);
```

### Localization Annotations

Always annotate user-facing strings with `@title` and `@description`:

```cds
entity Products {
  key ID    : UUID;
  code      : String(10) @title: 'Product Code';
  name      : String(255) @title: 'Product Name';
  price     : Decimal(15,2) @title: 'Price';
}
```

For i18n, use `{i18n>key}` references in annotation files:

```cds
annotate Products with {
  name @title: '{i18n>ProductName}';
}
```

## Common Mistakes to Avoid

```cds
// BAD: String without length
entity Orders {
  status : String;          // Always specify length: String(20)
}

// BAD: Using Integer as primary key (leads to sequence management pain)
entity Orders {
  key ID : Integer;         // Use UUID instead
}

// BAD: Storing currency amounts as Float
entity LineItems {
  amount : Double;          // Use Decimal(15,2) for money
}

// BAD: No default value for required status fields
entity Orders {
  status : String(20);      // Add default: String(20) default 'OPEN'
}

// BAD: Defining navigation in the schema that belongs in the service
// Keep schema clean; add filters/ordering in service projections
```

## Review Checklist

- [ ] Namespace declared at top of every schema file
- [ ] All entities use `UUID` primary keys (or inherit `cuid`)
- [ ] `cuid` and `managed` aspects applied where appropriate
- [ ] Enumerations defined as CDS types, not magic strings
- [ ] `Composition` used for parent-child (not `Association`)
- [ ] `Association` used for cross-entity references
- [ ] No `String` types without length
- [ ] No `Double`/`Float` for monetary amounts — use `Decimal`
- [ ] Services use projections and `excluding` to restrict field exposure
- [ ] Fiori/UI annotations are in a separate `*-fiori.cds` file
- [ ] User-facing elements annotated with `@title`
